# Pluribus

A MerrJep / FINN-style classifieds site for Albania. Rust (axum, sqlx, Askama) renders the pages on the server, Turbo and Stimulus make them feel instant in the browser, and PostgreSQL 15+ stores everything. The same pages can later be wrapped as iOS and Android apps with Hotwire Native.

## Running it locally

You need Docker and Rust 1.97 or newer. Start the database and the photo store, create your `.env`, and run the app, which applies the migrations at startup:

```bash
docker compose up -d
```

The photo store (Garage, see "Photos" below) needs a one-time setup after its first start, which creates its bucket and the app's key, the ones `.env.example` names:

```bash
sh dev/setup_garage.sh
```

```bash
cp .env.example .env
```

```bash
cargo run
```

Then open http://127.0.0.1:3000. Every setting is in `.env` (see "Configuration" below); the copied values work locally as they are. On Windows, use `127.0.0.1` rather than `localhost`: `localhost` tries IPv6 first, which adds about 200 ms to every request through WSL.

To keep the release build running there instead, as the development site, deploy it with the script (from WSL): it builds it, keeps the one running as the previous, restarts it on `BIND_ADDR`, checks it answers, and puts the previous back if it doesn't. It stops on a migration git doesn't know yet, which the server would apply, and rebuilds from clean when the binary is older than the sources (a build folder shared with another checkout):

```bash
dev/deploy.sh
```

`dev/deploy.sh --rollback` puts the previous one back.

To load the sample listings, from a bash shell. Their cover photos are free Unsplash photos, loaded from Unsplash's image CDN; the fixture credits each one.

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 < tests/fixtures/listings.sql
```

For a fuller site, also load 305 more listings across every category, each with a photo, a point on the map near its town, its seller's (fake) phone number, and the properties its category defines (a car's make, model, year, mileage, fuel, gearbox, body type and colour; a flat's rooms, area, floor and furnishing; and so on), so every filter has data to work on:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 < dev/sample_listings.sql
```

For a site at a real site's size, generate as many listings as you like (`dev/generate_listings.sql`): in every category, in about the shares a real site has them, each put together from lists of what Albanian listings say and cost ("Volkswagen Golf 1.6 TDI, 2012", "Shitet apartament 2+1, 95 m², Komuna e Parisit, Tiranë"), with the properties its category takes, a town and a point near it, a seller (a few with many listings, car dealers, agencies and shops among them), and two to four photos of its kind of thing (free ones from Unsplash, credited in the script). Runs add up; `-v seed=0.42` (between -1 and 1) repeats one, and `remove=1` takes out everything the script has made, and nothing else. 100 000 listings take about two and a half minutes:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v count=100000 < dev/generate_listings.sql
```

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v remove=1 < dev/generate_listings.sql
```

The sample listings, the test fixtures and listings from earlier versions of the script have only a cover; `photos=1` makes nothing new but gives each of them more photos of its category, two to four in all (a million listings take about a minute):

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v photos=1 < dev/generate_listings.sql
```

A generated property listing stands in the zone its title names where its town has zones ("…, Blloku, Tiranë"), so the zones have their averages a square metre. Earlier versions of the script left them in the town; `zones=1` makes nothing new but moves those into their zones:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v zones=1 < dev/generate_listings.sql
```

`only=<top-level category>` keeps making or removing to that category's listings (removing, with the sellers it leaves without any; making, with sellers and shops of their own): after electronics got their own properties (migration 0021), its listings were made anew with them:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v remove=1 -v only=elektronike < dev/generate_listings.sql
```

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v count=150000 -v only=elektronike < dev/generate_listings.sql
```

`views=1` makes nothing new but gives a twentieth of the active listings the script made two weeks of views (`listing_daily_stats`), most of them few and a few hundreds a day, so "Më të klikuarat" has rows to show before anyone has looked around; runs add up:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v views=1 < dev/generate_listings.sql
```

`drops=1` makes nothing new but makes a twentieth of the active listings the script made with a price (on sale, for rent or a service) 8 to 25% cheaper, rounded as people round prices, as if their sellers had lowered them, so the cards and pages have price drops to show (the price history's trigger records them); runs add up. Those who keep a listing hear only of the drops its seller makes on the site:

```bash
docker compose exec -T db psql -U marketplace -v ON_ERROR_STOP=1 -v drops=1 < dev/generate_listings.sql
```

The tests need the database running; each test gets a fresh database of its own, which is most of what a test costs. Two things keep that cheap. `compose.yaml` runs the development database for speed over durability (no waiting for the disk on each commit), with the lock memory and connections for a dozen test databases at once. And `dev/test_template.sh` makes the cluster's `template1` a migrated copy of the schema (sqlx-cli needed: `cargo install sqlx-cli --no-default-features --features postgres`), so that the `create database` behind every `#[sqlx::test]` copies 12 MB of files in a tenth of a second instead of running the 41 migrations, which the migrator then finds applied. Run it once after `docker compose up -d`, and again whenever `migrations/` changes: a new migration only costs the tests its own run until then, but a migration changed under the tests fails them all with "migration N was previously applied but has been modified". Scratch databases made with `sqlx database create` come migrated too. The 159 request tests then take about 13 seconds, eight at a time:

```bash
sh dev/test_template.sh
```

```bash
cargo test -- --test-threads=8
```

The tests' builds optimise every dependency, as the release does, and leave out rav1e's checks (`[profile.dev.package."*"]` in `Cargo.toml`): unoptimised, rav1e took seconds over each AVIF copy the photos' tests make, and image decoding and resizing are quicker too. The site's own crate builds as before; `media.rs` hands rav1e RGBA, since ravif's RGB path is inlined into the crate that calls it, where it ran twenty times slower.

`dev/check.sh` runs what a commit needs, clippy over every target and every test, side by side, each in a target directory of its own under `~/.cache` (a build there is far faster than one on a Windows drive from WSL), and prints only the warnings, the results and any failures; about 30 seconds once built. Given words, it runs only the tests whose names hold them, for while a change is being made:

```bash
sh dev/check.sh
```

```bash
sh dev/check.sh heading sort
```

Every test in `tests/web.rs` names the file's one embedded copy of the migrations, `#[sqlx::test(migrator = "MIGRATOR")]` (with `fixtures("listings")` after it when it needs the sample listings). A plain `#[sqlx::test]` reads all the migrations from disk and embeds them again for its test alone: with 120 tests, that was three quarters of the file's build, and rebuilding the tests after a change to them took 21 seconds rather than 5 to 9.

**Windows:** Rust's MSVC toolchain needs Microsoft's C++ build tools for its linker (`link.exe`): Visual Studio Build Tools with the "Desktop development with C++" workload. Without them nothing links, so build and run in WSL instead.

## How the frontend works

- Every page is plain HTML rendered by the server, so it loads fast and search engines index it as it is.
- The site speaks Albanian, and English for whoever chooses it: "English" at every page's foot ("Shqip" back), and in "Cilësimet", keeps the choice a year in a cookie (`gjuha`) and on a signed-in user's account; one made before signing in becomes the account's (`web/language.rs`). A visitor who hasn't chosen and whose browser reads no Albanian (a foreigner's, or the phone of someone abroad) is offered English at the top of the page, in English, until they choose either. Every text a page or a script says goes through `t` (`src/i18n.rs`, `i18n.js`), keyed by its Albanian, which is what the templates read as and what a page says where the catalogue has no English (`i18n/en/`, which `build.rs` makes a sorted table of); so do the database's own labels, at render (the categories, the properties' names, their choices and units, the promotions: `data.txt`), and a property's value by `t_value` ("148 000 km", "6,1 inç", "1 month"). A test fails the checks for any text given `t` without its English. The language is a task-local the language layer sets around each request, so templates and handlers need nothing passed; numbers take a decimal point in English and dates read "4 Oct 2026". The pages about the site have their English whole, the terms' and the privacy page's saying the Albanian applies. What goes out on its own speaks the language kept on its recipient's account: the notices of unread messages, the saved searches' alerts, the expiry warnings, a store's invitation by e-mail; a sign-in code's e-mail speaks that of the page that asked for it. WhatsApp's templates stay Albanian, as Meta approved them. The notifications keep their titles in Albanian, as the site wrote them, and the notifications' page words them anew for an English reader. What people wrote (titles, descriptions, messages, names), the names of towns and brands, and the moderators' pages stay as they are. Search reads Albanian words, and on an English page English's for a category, a kind and the words that join them ("flat for rent in Tirana"); numbers are read as either language writes them ("9,500", "12.5"). The addresses stay the same in both languages, and search engines read the Albanian.
- The pages are in Albanian and say so (`<html lang="sq">`), so a browser with a translator of its own offers to translate them for a visitor who reads another language: Chrome and Edge do, Google's and Microsoft's translators knowing Albanian. What a translator would turn into ordinary words keeps its name (`translate="no"`): people's and stores' names (a card's seller, the seller card's name, a profile's or a store's heading, a conversation's other side, the inbox's names; "Besa" would come out "Faith", "Drita" "Light"), places (a card's place line and town, a listing's place and its map's: "Blloku" would come out "the Block", "Kombinat" "combine"), the wordmark, and a revealed number or address. Prices stay translatable: a translator keeps the figures, and "Çmimi me marrëveshje" is better read translated. An English interface of the site's own would need every page's words in two languages, and the notifications, which are kept as finished sentences, kept otherwise; the categories' and properties' names have their `*_i18n` columns waiting.
- Every page says what it is in its head (`web/seo.rs`, `meta.html`): to search engines, a description and its canonical address; to the apps that preview a shared link (WhatsApp, Facebook, Messenger, X, Telegram, iMessage...), the Open Graph tags they show it with. A listing's preview has its title and price ("Mercedes-Benz C 220, 2018, automatike · 21 500 € (i diskutueshëm)"), where it is, what kind of listing and in what condition followed by the start of its description ("Durrës · Në shitje · E përdorur — Importuar nga Gjermania..."), and its first photo; a category's, its name, how many listings it has and its first listing's photo; a seller's profile, their name, since when they are on the site and how many listings they have. The welcome page, and any page without a photo of its own, show the site's picture (`static/img/pluribus.png`: the wordmark and "Njoftime në gjithë Shqipërinë" under it on the page's grey, 1200 × 630, both small enough to stay whole where an app crops the picture square). A listing with a price also gives it as `product:price` tags, and one on sale tells Google what it sells, as schema.org data: a Product and its Offer, with the price, the currency, the condition, whether it is still for sale (in stock, reserved, sold) and the seller, a person or an organization.
- A category page's canonical address keeps its filters but not its order, its page or the map's dots, so `/c/makina?sort=price_asc` counts as `/c/makina` and `/c/makina?vehicle_fuel=DIESEL` as a page of its own. A search's results (`/search`, the map page, a category's or a seller's searched with words) and a sold listing ask search engines to leave them out of their results (`noindex, follow`) but to follow their links to the listings. `/robots.txt` keeps crawlers out of a visitor's own pages and names `/sitemap.xml`, which lists the pages' sitemap (the welcome page, every category's, and the businesses' with listings) and the listings', one for every 50 000 listing numbers (Google reads at most 50 000 addresses from one), each listing with the day it last changed. Every address they give starts with `PUBLIC_URL` (see "Configuration") or, without it, the address the request came to.
- Turbo fetches pages and form responses in the background and swaps them in without a full reload. It also prefetches links on hover.
- Listing pages load the next page as the visitor scrolls near the end. A `<turbo-frame loading="lazy">` points at the next page, and the server answers that request with just the frame. Asked for without the frame (by a search engine, or a link opened anew), the same address is the whole page, so every page says it differs with `Turbo-Frame` (`Vary: Turbo-Frame, Cookie, Accept-Language`, `web::render`, the language's cookie and the browser's languages too), and a cache keeps the two apart rather than giving the frame to a visitor or a search engine. Cloudflare caches no HTML unless a rule tells it to, and then takes `Vary` into account only with its Cache Rules' Vary setting; the pages differ with cookies too (the town remembered, the cards' view, the sellers blocked, the language), so their HTML isn't for a shared cache as they are.
- Small updates come back as Turbo Streams. For example, the phone button ("Shfaq numrin") swaps in the phone number and counts the reveal.
- The little JavaScript there is lives in Stimulus controllers in `static/js/controllers/`, like the share button.
- Under a mouse, Turbo fetches a link ahead as the pointer rests on it; on a phone, a link starts fetching as soon as a finger touches it, any link Turbo would fetch ahead under a mouse (to another page of the site, not opened elsewhere, nor one that opts out with `data-turbo-prefetch="false"`, as "Raporto" does, nor one that leads a frame inside the page), and the visit the tap makes takes that response (`application.js`), so the page is on its way while the finger is still down: a category's pill, the chip that takes a filter off, "Shiko të gjitha" as well as a listing. A finger that moves, scrolling, drops it. A tap's head start is only the tap's own length, though, about a tenth of a second, where a mouse resting on a link gives a click most of a second, and a page's round trip is longer than a tap; so on a touch screen the page behind a link is fetched ahead once the link has been on screen for 75 ms: one the visitor stops on, not every one a swipe flicks past (a link that leaves sooner starts its wait again when it comes back; the cards' listings, the categories' pills), two at a time, the next as one finishes, and at most twelve a page, quietly, each kept half a minute for the visit a tap makes, as the touch's own is: not where the visitor asks to save data, nor on a connection the browser calls slow (`navigator.connection`).
- A listing's first photo loads ahead of anything else on its page (`fetchpriority="high"`), so it shows as soon as it can. So does the first photo of a page's first row or grid of cards (`ListingPage::lead`): on the welcome page the first of "Më të klikuarat", or without it the newest listings' first; on a category page the first of its "Më të klikuarat", whose first two photos load straight away, or without it the results' first (not on the map page, whose map comes first). ### Stylesheets

`static/css/`, eight files, which pages get as one stylesheet, `/static/css/site.css` (`web::site_css`): the eight one after the other in this order (`web::STYLESHEETS`), minified (`web::minified`): without their comments, which are half their bytes, and with no more white space than the browser needs, one space kept where it parts two words (before "(" too, as "and(" would be a function) and none round the punctuation that ends or joins rules (38 KB gzipped as written, 18 without the comments, 17 minified). Every page renders the same from it as from the eight files: compared element by element, every computed property and those of `::before` and `::after`, on the welcome page, a category (Elektronikë's in its blue, and Prona's big cards), a listing, the posting form and the map on a wide screen, the only differences were custom properties, whose text browsers keep as written ("a,b" for "a, b"), which give the same values where they are used. A page shows nothing until its stylesheets have come, and one request comes sooner than eight: Lighthouse counted 300 ms for the eight through the tunnel. Every page also names it in a `Link: <…>; rel=preload; as=style` header (`web::render`), which Cloudflare, in front of the site's own domain, sends ahead as a 103 Early Hints answer, so the browser fetches the stylesheet while the origin is still building the page; a quick tunnel passes the header on as it is, and the browser starts the preload as the page's headers arrive. The server reads the files each time it is asked for it, as it serves the files themselves, so a change shows at once; at the fingerprinted address browsers keep it for good. The cascade follows the order, so a rule meets the others where it would in one file. Colours, sizes and weights are custom properties in `base.css` (`--accent`, `--button`, `--text-sm`, `--semibold`...), with the dark theme's values beside the light theme's. `--gutter` (1rem: 14 px on a phone, 16 on a computer) is the room between the page and the screen's sides (`.container`), and as much stands between the header and the first line of the welcome page, of a category page and of a listing's page (its path; `.listing` in `listing.css`).

Buzz. To add one, write a migration like 0013's, or approve one a seller typed.

To add a property, write a new migration:

```sql
INSERT INTO attributes (code, name, name_i18n, data_type, unit)
VALUES ('tv_refresh_rate', 'Frekuenca', '{"en": "Refresh rate"}', 'NUMBER', 'Hz');

INSERT INTO category_attributes (category_id, attribute_id, filterable, show_in_card, sort_order)
SELECT c.id, a.id, true, false, 45
FROM categories c, attributes a
WHERE c.slug = 'televizore' AND a.code = 'tv_refresh_rate';
```

How each type of property is offered as a filter:

| Type | Filter | In the URL |
|---|---|---|
| SELECT with up to 8 options | checkboxes; a listing matches any ticked option | `property_rooms=R21&property_rooms=R31` |
| SELECT with more options, or dependent on another (model under make) | dropdown; dependent options are grouped by their parent and narrow to the chosen parent, the others' groups hidden in the page for when it changes; an option under another parent filters nothing | `vehicle_make=BMW` |
| MULTISELECT | checkboxes; a listing must have every ticked option | `vehicle_features=ABS&vehicle_features=NAVIGATION` |
| NUMBER | from and to | `vehicle_year_min=2015&vehicle_mileage_max=150000` |
| BOOLEAN | one checkbox | `<code>=1` |
| a pair of NUMBERs, `<x>_from_year` and `<x>_to_year` (the years a part fits) | one year, the buyer's vehicle's ("Viti i automjetit"); a listing matches unless its years leave that year out, so one that doesn't give its years still shows | `fits_year=2015` |

TEXT and DATE properties appear on the listing page but not as filters.

- Subcategories inherit their parents' properties, from every level above them. The `effective_category_attributes` view resolves that, and where a subcategory configures a property its parent has too, the subcategory's settings win. A subcategory can't leave out one it inherits, so a property only some kinds have sits on those kinds: Prona's rooms on Apartamente and Vila / shtëpi, not on Prona, whose Truall has none.
- A category can offer only some of a property's options, in its own order (`category_attribute_options`, migration 0021): phones' brands aren't cameras', and a laptop's storage starts at 128 GB where a phone's starts at 32. The form, the filters and the generator's check all read `category_options(category, property)`, which gives a category's own list where it has one and otherwise every option, as a parent category's filters offer every brand. An option a seller typed and a moderator approves is offered in the categories it was typed in, before "Tjetër". Migration 0023's shared lists work the same way: shoes' brands aren't watches', nor a dog's breeds a cat's, and a garden's materials aren't a dress's.
- `category_attributes.label` is a category's own name for a property, where the property's name would mislead: on a part, "Marka" would read as the part's own brand, so there it is "Marka e automjetit". It is inherited like the other settings; NULL means the property's name.
- Property codes become URL parameters, so don't name one `q`, `category`, `city`, `zone`, `lat`, `lng`, `radius`, `type`, `condition`, `price_min`, `price_max`, `currency`, `sort`, `after`, `harta` or `numri`; a year pair's filter takes `<x>_year` too.
- A property whose code ends in `_year` can't be later than next year, and in a year pair the second can't come before the first.
- `categories.listing_types` lists the kinds of listing a category takes (sale, wanted, rent...); with more than one, the filter offers them. `categories.uses_condition` is false where new or used means nothing: property, jobs, services and pets.
- Searchable property labels reach full-text search through `listings.search_extra`, followed by the names of the listing's category and of those above it, in Albanian and English, and of its place (migration 0017). After saving a listing's values, category or place, run `UPDATE listings SET search_extra = listing_search_extra(id) WHERE id = $1`; that is how "telefon" finds an iPhone, and "laptop shkoder" the laptops in Shkodër. Renaming a category or a place calls for the same for its listings.
- `format_attribute_number(value, unit)` formats numbers for display: grouped with the unit when there is one ("148 000 km"), as they are when there isn't (a year).

The cards' three are AVIF too (rav1e, Rust's AV1 encoder, by way of ravif and the `image` crate; quality 78, speed 6), for the browsers that show it, which today is all of them: over twelve of the site's photos, measured against a lossless copy of each, the AVIF ones came as close to the photo as the WebP ones by SSIM (closer for half of them, less close for the other half) and closer by PSNR, and about a fifth lighter (a card's 13.3 KB rather than 17.2, a small one's 6.9 rather than 8.9): 78 is the quality where the two met, 75 a little short of the WebP ones and 80 a little past them. rav1e takes about 0.45 s over a card's copy and 0.2 over a small one, without the assembly NASM would build (libwebp a hundredth of that); at speed 10 it would take a third of the time for files a fifth heavier. ## Database

The application applies the migrations at startup with `sqlx::migrate!()`, which embeds `migrations/` in the binary; `sqlx migrate run` does the same from the command line. sqlx stores a checksum of every migration it has run and refuses to continue if one changes, so add schema changes as new files (`migrations/0014_<description>.sql`) instead of editing the existing ones.

## Important architectural choices

### 1. Authentication is external

Passwords are deliberately not stored in this schema. `users.auth_subject` maps to Keycloak/Auth0/Cognito/etc. Staff roles (moderator, admin) come from the identity provider as well.

### 2. Dynamic category fields are normalized and type-checked

Do not create a `listings` table with hundreds of nullable columns such as `mileage`, `floor`, `screen_size`, `engine`, etc. Instead:

- `attributes`, `attribute_options`, `category_attributes`
- `listing_attribute_values`: one row per listing and attribute, for TEXT, NUMBER, BOOLEAN, DATE and SELECT
- `listing_attribute_options`: one row per chosen option, for MULTISELECT

The usual weakness of this design is that any value can end up anywhere. Here the database prevents that:

- `listing_attribute_values.data_type` must equal the attribute's type (composite foreign key to `attributes(id, data_type)`), and a CHECK then requires the matching value column. An attribute's type can't change while values exist.
- Options are referenced as `(attribute_id, option_id)`, so a listing can't store `vehicle_fuel = MANUAL`.
- A SELECT value is a single `value_option_id`, so the primary key allows one per listing. Only MULTISELECT uses `listing_attribute_options`.

When inserting a value, copy `data_type` from the attribute. Leave `listing_attribute_options.data_type` out of inserts; it defaults to `MULTISELECT`.

Still the application's job: which attributes a category has and which are required, `validation_json` ranges, and that the chosen model belongs to the chosen make (`attribute_options.parent_option_id`), and that a part's years don't end before they start.

Attributes are inherited down the category tree. A listing in Makina (Cars) gets the attributes of Makina and of Automjete (Vehicles), and the nearest category's settings win (query below). `categories.allow_listings = false` marks categories that only group subcategories.

### 3. Media belongs in object storage

Do not store image/video blobs in PostgreSQL. Store them in an S3-compatible store (Garage locally, Cloudflare R2 in production; see "Photos") and keep only keys/URLs/metadata in `listing_media`. Rows start as `PROCESSING`; only `READY` media is shown, after virus scanning and moderation. `sha256` finds the same photo reused across listings, a common scam signal.

### 4. Search can start in PostgreSQL

- PostgreSQL has no Albanian stemmer, so `sq_unaccent` is the `simple` configuration plus accent folding: "shtepi tirane" finds "Shtëpi me qira në Tiranë". Use the same configuration in queries.
- Search forgives typos and finds a word's other forms (migration 0016): "golff" finds the Golfs, "makinat" the listings that say "makinë", "apartamente" the "Apartament". `search_query(words)` turns the words into the tsquery listings are matched against: the websearch syntax as before (`-word`, `"a phrase"`, `or`), each word of four letters or more widened, where it stands, to its other forms (the words listings use with the same rough stem, `sq_stem`: makina, makine, makinat, makinave → makin) and, when few listings use it or none do, to the common word it most likely misspells (`search_correction`: spelt alike by `pg_trgm`, used by more than three times as many listings) with that word's forms. A word many listings use is never corrected, so "audi" stays apart from "audio". It also returns the corrections, which the page names under its heading ("Shfaqen edhe rezultatet për „golf“."). The first eight words are widened; at most 100 characters of search words are taken.
- A listing's category, those above it and its place are words of it too (`listing_search_extra`, migration 0017), so a search finds listings by them as by anything they say: "apartamente tirane" finds the flats in Tirana, "goma" what is under "Goma / disqe", "cars" the cars, "shkodra" and "shkoder" the listings in Shkodër (a town in -ër is kept with its article as well, as one ending off doesn't turn either into the other). As words rather than filters, they combine with the rest of a search: "makinë larëse" finds washing machines, which say "larëse", not cars, which only say "makinë". `search_query` leaves out filler words (në, me, për, dhe, e, i, të, një, nga, tek, që), which a listing would otherwise have to say as well: "apartament me qira në tiranë" searches apartament and tiranë, among listings for rent (below); a search of fillers only keeps them. "se" is no filler, for the iPhone SE. "ose" and "apo" mean or: "shtëpi ose vilë".
- Words that name a category, a kind of listing or a town put those filters on (`web/named.rs`): "apartament me qera ne tirane" goes to `/search?category=apartamente&city=tirane&type=RENT`, the flats for rent in Tirana, where each is a chip to take off if it was misread, and the words that name nothing stay searched there ("golf 7 në Durrës": golf 7, in Durrës). Searched as words, they found the listings that say them in any category, with none of the category's filters (rooms, floor, furnished) to narrow them. A town is named in any of its forms (Tirana, Tiranës, Durrësi, Shkodra, Kamza, Gramshi) or by its two or three words (Malësi e Madhe), one of three letters (Mat, Has) only after a word that leads to a place ("në Mat"; "bojë mat" is a colour), and words that name two towns name neither. A town's zone only where the search is about property, the page's category or the one the words name being Prona or under it: "apartament 2+1 në Plazh" goes to `/search?q=2%2B1&category=apartamente&city=durres&zone=plazh`, the flats in Plazh, in Durrës, "2+1" searched there; elsewhere its name stays a word ("peshqir plazhi" is a beach towel). A zone is named as a town is, in its forms (Plazhi, Bllokut, "në Bllok", Qendra) or by its few words, the first in any of its forms (Komuna e Parisit, "në Komunën e Parisit", "Rrugën e Durrësit"), and read before the towns, as some zones are named after one (Rruga e Durrësit is in Tirana); it puts its town on too. A name the zones of several towns share (Qendër) is the one in the town the words name, or else in the page's; a zone in another town than the one named stays a word, the town kept, and two zones name none. A kind of listing by the words `search_kind` knows (below), when the category takes that kind and another. A category only in a search across every category, by the first word that is no filler, verb an ad starts with (kërkoj, jepet, ofrohet), kind or town, as the thing sought comes first ("kufje për telefon" is headphones); the word names the categories whose name is about it in any of its forms, a name being about its first word and those a "/" (or "dhe") joins to it ("Vila / shtëpi"; "Tapete makine" are mats, so "makinë" is Makina). Of several, the one that takes the kind named, then the one whose name has most of the search's words, most of them as typed, then the shortest name; two still alike name neither: "shtëpi" alone stays a word, as Vila / shtëpi and Shtëpi / kopsht are both about it, but "shtëpi me qira" is Vila / shtëpi, the one that takes rentals. A category's own page reads only the towns and the kinds in its search; the map's pin says where, so it reads none.
- A word that names a kind of listing finds the listings of that kind, as well as those that say it (`search_kind`, migration 0024): shitje, shitja, shitet, shes for sale, qira, qera for rent, blej for those who want to buy. Few cars for sale say "shitje", so "golf 7 në shitje" found nothing while every word had to be in a listing; now it finds the Golfs for sale, and "makina me qira" still finds a rental firm's listing that says "qira", whatever its kind. `search_query` returns such words apart from the rest (`kinds`, and `kind_query`, the words with their forms), and the listing queries take a listing of one of the kinds or one that matches `kind_query`; a word left out ("-shitje") stays a word left out.
- The words listings use are the materialized view `search_words`, from `ts_stat` over the active listings' search vectors. The app rebuilds it at startup and every 15 minutes (`REFRESH MATERIALIZED VIEW CONCURRENTLY`, which searches go on through; about 2 s for 100,000 listings), so a new listing's words reach typo correction within a quarter of an hour, while the listing itself is searchable at once. `tests/fixtures/listings.sql` and `dev/sample_listings.sql` end by refreshing it, and so should anything else that loads listings with psql: `REFRESH MATERIALIZED VIEW search_words;`. The zones' averages a square metre (`zone_area_prices`) and what cars of each model ask (`car_model_prices`) are rebuilt along with it; after loading listings with psql, rebuild them too: `REFRESH MATERIALIZED VIEW zone_area_prices; REFRESH MATERIALIZED VIEW car_model_prices;`.
- Pages work a search out once, before their listing queries (`db::text_search`), and pass it to them as a parameter. Worked out inside them, it would be hidden from the planner, and a search that finds nothing would walk the whole newest-first index: 87 ms instead of 0.04 ms on 161,000 listings.
- Even seen, words fool the planner, both ways: it takes each word for as common among a category's listings, or alongside another word, as among all of them. For words that seldom meet it walks the newest first order (or, for a count, the table) expecting a match soon: "makine apartament" goes to the word apartament among the cars, and on the development database's million listings its page took 2.1 s, its ranked window reading all 921,042 active listings (2.9 s in psql), its count and categories each the table (225 ms). For words that meet often it reads every match and sorts them: the window of "gjendje shumë mirë" (51,549 matches) took 92 ms that the walk does in 4. Counting the matches first would tell, but a word in a quarter of the listings would pay for it on every page (29 ms for "makina"). So every query of a search with words runs as planned for `FIRST_TRY` (50 ms, a `statement_timeout` in its transaction), which the plans that suit their matches need a few milliseconds of. Past it, the matches are counted through the words' index up to `FEW` (5,000; `ListingFilter::matches` keeps the answer for the page's later queries, which skip the first try), and the query runs again: for few matches with bitmap scans alone (`enable_indexscan` and `enable_seqscan` off, no parallel workers), sorted; for many in order (`enable_bitmapscan` and `enable_seqscan` off), the walk then finding them soon, but for a count or the categories, which want any matches and which the walk could take a long way for ("samsung" among the phones, 18,929 matches, counted to 1,001 in 480 ms walking, 5 through the index), through the index all the same (`db::planned`). The words' index has the category in it (`idx_listings_active_words`, migration 0038, a GIN index of both through `btree_gin`), so "these words in these categories" reads no listing that doesn't match. Against the million listings, the page of "makine apartament" now takes 160 ms, the first try's 50 included, and that of "gjendje shumë mirë" 97 instead of 215; pages whose plans suit their matches ("golf", "makina", "iphone", 15 to 20 ms) are as they were.
- The search vector weights the title (A) above searchable attribute labels (B, from `listings.search_extra`) and the description (C), so `ts_rank` puts title matches first, as the best match first order has it.
- `sort_at = greatest(published_at, bumped_at)` is the "newest first" key. A bump lifts a listing to the top, and newer listings then push it down. Featured listings get their own slot rather than being sorted into every page.
- Browse and search indexes are partial (`WHERE status = 'ACTIVE'`). After a year most rows are expired or sold, and this keeps the hot indexes small.
- Listings are priced in ALL and EUR. Filter and sort on `price_normalized`, never on `price_amount`. It holds the price in euros, computed with `price_in_eur(amount, currency)` from the `exchange_rates` table; price filters convert their bounds with the same function, so the two always agree. Free listings count as 0; "price on request" has no price and sorts last. The rate is the Bank of Albania's (`rates.rs`): every six hours the server reads its official rate off its page, which it publishes each working day around noon with no feed ("Last update: 09.10.2026", the main table's EUR row, 91.65 lekë a euro, checked to be between 50 and 200), and takes it when it is half a percent or more from the one prices are worked out at (`db::RATE_STEP`), as `round(1 / rate, 8)` with its day (`rate_date`); the seeded 100 lekë a euro was a round placeholder, 9 % off. Taking it makes the euro prices of the listings priced in lekë due to be worked out again (`normalized_at` emptied): 2 000 at a time by id, each batch a short transaction with a fifth of a second between, so that pages' queries go between them, and only those whose price isn't what the rate makes it, a free one without an amount keeping its 0. Rewriting a listing means its indexes and its search vector made again: the first pass on the development database, from the placeholder to 91.65, rewrote 449 709 listings in 116 s while its pages went on answering in their usual 8 to 17 ms (a few slower, up to 180), which is why a rate that moves a few hundredths a day isn't taken each day. The pass leaves each listing's `updated_at` as it was, which the sitemaps give search engines (`app.keep_updated_at`, migration 0032), and one the server stopped in the middle of goes on at its next start; a page of the bank's changed past reading stops nothing but the rate, and says so in the log.
- Trigram indexes on unaccented titles and location names support autocomplete ("korce" finds Korçë).
- Unfiltered, a page reads only its 24 listings off an index already in its order rather than sorting the category: newest first `idx_listings_active_sort`, by price `idx_listings_active_category_cheapest` and `_dearest` (on `coalesce(price_normalized, ±Infinity)`, the price order's key), nearest first `idx_listings_active_category_earth`, a GiST index of the category and the place that gives listings nearest first (KNN). `category_id = ANY(...)` can't use an index for an order, so by price or distance a page over several categories reads each one's first in its own index and merges them (`db::push_ordered`, a LATERAL scan per category); one index of every category's listings in price order would wade through the others' whenever they come first. A category's cheapest first went from 160 ms on half a million listings to 10 ms on a million, and the nearest within 10 km of Tirana from 630 ms to 23 ms.
- The site's connections plan every query for the values it runs with (`plan_cache_mode = force_custom_plan`, set as they open: `db::plan_for_values`). By default, once a connection has run a prepared query five times, Postgres may plan it once for any values (a generic plan), and a filter's values match a handful of listings or tens of thousands, which no one plan suits: on the dev database's million listings, one request in ten for the cars filtered to BMW took 107 ms or more, and half of those for diesel automatics 109 ms or more; planned for their values, they take 16 to 18 ms. Planning every query costs the other pages about a millisecond.
- Radius search ("within 10 km") uses the `cube` and `earthdistance` extensions rather than PostGIS. A listing's point is `listings.latitude`/`longitude`, and the partial GiST index `idx_listings_active_earth` covers the active listings that have one: a 5 km search around Tirana's centre takes about a millisecond (query below). Distances are the cube's `<->`, straight through the earth, which the index orders by; over the surface they would be under 15 cm longer at 50 km. Municipalities have points too, at their seats (from Wikidata, CC0).

This is enough for an MVP and a fairly large site: each example query below ran in under 10 ms against 200,000 listings. When traffic grows, mirror active listings into OpenSearch/Elasticsearch, fed from `outbox_events` so the index never misses a change.

### 5. Analytics are aggregated

`listing_daily_stats` stores daily counters rather than one database row per page impression. Buffer increments (in memory for now: `views.rs` writes the pages seen once a minute; Redis once there are several servers) and flush them periodically, because an UPDATE per page view turns popular listings into lock hot spots. High-volume raw events should go to Kafka/ClickHouse/BigQuery/etc. if needed.

### 6. Users are anonymised, not deleted

Foreign keys follow one rule:

- Data that only matters to the user (favorites, saved searches, notifications, device tokens, preferences, verifications, blocks, memberships, chat read state) is deleted with them (`ON DELETE CASCADE`).
- Anything other people rely on (listings, messages, reviews, reports, moderation actions, payments, history) blocks a hard delete.

A user who never did anything can be deleted outright. Everyone else is anonymised in one transaction:

"Fshi llogarinë" in "Cilësimet" does this (`db::delete_account`, `settings::close`), once FSHI is typed:

1. In `users`, set `email`, `phone_e164`, `avatar_url` and `notice_token` (the links that stop its e-mails) to NULL, `display_name` to "Përdorues i fshirë", `auth_subject` to `'deleted:' || id`, `status` to `DELETED` and `deleted_at` to `now()`. A CHECK constraint refuses a DELETED user who still has an e-mail address or phone number. The phone number and the address are free again, for a new account.
2. Delete their sessions, device tokens, notifications, notification preferences, saved searches, saved listings, favorites, verifications, blocks either way, business memberships and the sign-in codes asked for their contacts.
3. Set their listings to `DELETED` (the status history saying "Llogaria u mbyll"); delete their `listing_contacts` rows and their media, then every copy of each photo in the store (`photos::delete`). The stores they own close with them (`businesses.status` `DELETED`, their logos and covers out of the store), their listings too, whoever of their people posted them, with their people and invitations; the listings they posted for someone else's store stay that store's.
4. Keep their messages for the other party, under "Përdorues i fshirë", as the privacy page says (a lawyer may still want bodies blanked after a while).
5. Keep payments (accounting retention), reports and moderation actions (for a limited period) and reviews (shown under "Deleted user").
6. Delete the account in the identity provider.

Financial rows are never cascade-deleted.

### 7. Payments are idempotent

`payment_orders` is one checkout, `payment_order_items` is what was bought (promotion for a listing, subscription period, fee) at the price paid, and `payment_transactions` records provider events. Every provider retries webhooks, so:

- `(provider, provider_order_id)` and `(payment_order_id, transaction_type, provider_reference)` are unique;
- each webhook is first inserted into `payment_webhook_events`, in the same transaction that processes it. If `ON CONFLICT DO NOTHING` returns no row, it was already handled.

`listing_promotions.payment_order_item_id` links a promotion to the item that paid for it (NULL when included in a plan). `listings.featured_until` and `bumped_at` are copied from active promotions for fast sorting. HIGHLIGHT's are copied into `highlighted_until` (migration 0040), and CATEGORY_TOP's return to the top every day moves `bumped_at` (`db::tick_promotions`); HOMEPAGE has no product, and nothing shows it yet. Until there are payments, moderators give promotions (`/moderim`, `db::grant_promotion`), with no `payment_order_item_id`.

## Conventions

- **IDs** come from `uuid_v7()`: time-ordered, so inserts append to the index instead of scattering across it. On PostgreSQL 18+, use the built-in `uuidv7()`. A v7 id reveals its creation time.
- **Listing URLs** use `public_no`: `/listing/12345-vw-golf-7`. The slug is cosmetic and not unique.
- **Enumerations** are `varchar` + CHECK: easy to extend in a migration, and they map to Rust enums by name.
- **Language**: labels (`name`, `label`, `description`) and category slugs (`automjete`, `makina`) are Albanian. Other languages go in the `*_i18n` columns, e.g. `{"en": "Vehicles"}`. Read them with `coalesce(name_i18n ->> :lang, name)`, which falls back to Albanian.
- **Currency**: listing prices default to lekë (`ALL`). `categories.default_currency` preselects euros for cars and property, which Albanian sellers price in EUR.
- **Timestamps** are `timestamptz`, and `updated_at` is set by trigger. The history tables use `clock_timestamp()` so several changes made in one transaction stay in order. Compute calendar days (`listing_daily_stats.stat_date`, daily digests) in `Europe/Tirane`, not UTC, or set the database default with `ALTER DATABASE <name> SET timezone = 'Europe/Tirane'`.
- **History is automatic**: triggers write `listing_status_history` and `listing_price_history`, so don't insert those rows yourself. To record who changed a status and why, run `SELECT set_config('app.user_id', $1, true), set_config('app.status_reason', $2, true);` earlier in the same transaction.
- **Chat**: start conversations with `INSERT ... ON CONFLICT (listing_id, buyer_user_id)` (below; `db::start_conversation`). A message's sender must be a participant. A business's listing reaches whoever posted it; add the business's other members as participants when they open a thread, for a shared inbox.
- **Phone numbers** are E.164 (`+355691234567`) and currencies are upper-case ISO 4217 codes (`e164_phone` and `currency_code` domains).

## Using it from Rust (sqlx)

- **Checked queries:** use `query!` / `query_as!` for fixed queries; they're checked against the real schema when you compile. Set `DATABASE_URL` for local builds, and commit the `.sqlx` folder that `cargo sqlx prepare` writes so builds without a database still work.
- **Search page:** build it with `QueryBuilder`, adding a condition and a bound value for each filter the user set. These queries aren't checked at compile time, so cover them with tests.
- **Types:** enable sqlx's `uuid`, `time` (or `chrono`), `rust_decimal` and `json` features, so `uuid`, `timestamptz`, `numeric` and `jsonb` map to `Uuid`, `OffsetDateTime`, `Decimal` and `Json<T>`. Never select `search_vector`, which has no Rust type; only filter on it. If a macro rejects the `e164_phone` or `currency_code` domains, cast to text in SQL (`$1::text`).
- **Nullability:** the macros infer whether each column can be NULL and sometimes guess wrong, for example after a LEFT JOIN. Override with `AS "name!"` (never NULL) or `AS "name?"` (may be NULL).
- **IDs:** columns default to `uuid_v7()`. If you'd rather create IDs in Rust, `Uuid::now_v7()` from the `uuid` crate produces the same kind.
- **Tests:** `#[sqlx::test]` gives each test a fresh database with `migrations/` applied; in `tests/web.rs`, write it `#[sqlx::test(migrator = "MIGRATOR")]`, so the migrations are embedded once rather than once per test. `tests/schema_checks.sql` is a psql script, and cargo ignores `.sql` files in `tests/`.

## Typical listing creation flow

1. User selects a category (one with `allow_listings = true`).
2. Backend loads the category's attributes, including those inherited from parent categories.
3. User fills common listing fields and required category attributes, and, for a property or a car, can put a pin on a map for the listing's point ("Vendi në hartë", kept to about a hundred metres, near the town chosen). Without one, use the town's point (`locations.latitude`/`longitude`): a listing with no point never appears in map searches. The listing's `listing_contacts` row holds the number buyers see behind the phone button: by default the seller's own, or the business's `public_phone`. Without one, the listing page has no phone button.
4. Backend validates values against `validation_json` and the options, including make → model.
5. Listing is inserted as `DRAFT` (the price may still be missing) or `PENDING_REVIEW`, with `created_by_user_id`. Attribute values are inserted with their `data_type`, then `search_extra = listing_search_extra(id)` copies the searchable labels into full-text search, and `price_normalized = price_in_eur(price_amount, currency)`.
6. Images are uploaded to object storage and rows are inserted into `listing_media` as `PROCESSING`; a worker marks them `READY` after scanning.
7. Moderation or automatic rules approve it (`moderation_actions.moderator_user_id` is NULL for automatic decisions).
8. Listing becomes `ACTIVE` with `published_at` and `expires_at`, and an outbox event is written for search indexing and saved-search alerts.

## Query examples

Attribute and option ids are reference data: cache them by code in the application and pass the ids. Placeholders like `:category_ids` stand for bound parameters (`$1`, `$2`, … in sqlx).

### Browse a category, newest first

```sql
SELECT l.id, l.public_no, l.slug, l.title, l.price_amount, l.currency, l.sort_at
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.category_id = ANY(:category_ids)                -- the category and its descendants
  AND (l.sort_at, l.id) < (:last_sort_at, :last_id)     -- omit on the first page
ORDER BY l.sort_at DESC, l.id DESC
LIMIT 30;
```

Keyset pagination costs the same on page 50 as on page 1. OFFSET gets slower with every page, and shows duplicates when a bump reorders listings between page loads.

### Sort by price

Listings without a price come last in both directions, so a missing price counts as infinitely high (cheapest first) or low (most expensive first). That keeps the keyset a plain row comparison:

```sql
SELECT l.id, l.title, l.price_normalized
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.category_id = ANY(:category_ids)
  AND (coalesce(l.price_normalized, 'Infinity'), l.id)
      > (coalesce(:last_price, 'Infinity'), :last_id)   -- omit on the first page
ORDER BY coalesce(l.price_normalized, 'Infinity'), l.id
LIMIT 30;
```

Most expensive first: `'-Infinity'`, `<` and `DESC`.

### Within a radius, nearest first

```sql
SELECT l.id, l.title,
       earth_distance(ll_to_earth(:lat, :lng), ll_to_earth(l.latitude::float8, l.longitude::float8)) AS meters
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.latitude IS NOT NULL
  AND earth_box(ll_to_earth(:lat, :lng), :radius_m)
      @> ll_to_earth(l.latitude::float8, l.longitude::float8)          -- the index: a box around the circle
  AND earth_distance(ll_to_earth(:lat, :lng), ll_to_earth(l.latitude::float8, l.longitude::float8))
      <= :radius_m                                                     -- the circle itself
  AND (earth_distance(ll_to_earth(:lat, :lng), ll_to_earth(l.latitude::float8, l.longitude::float8)), l.id)
      > (:last_meters, :last_id)                                       -- omit on the first page
ORDER BY meters, l.id
LIMIT 30;
```

The index only applies when the query repeats its expression, `ll_to_earth(latitude::float8, longitude::float8)`, and its condition, `status = 'ACTIVE' AND latitude IS NOT NULL`, word for word.

### Featured slot

```sql
SELECT l.id, l.title
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.category_id = ANY(:category_ids)
  AND l.featured_until > now()
ORDER BY random()
LIMIT 4;
```

`db::featured_cards` runs it with a browse page's whole filter in place of the categories alone (its words, its place, its price...), up to `FEATURED` (8), for the row over the results; the partial index `idx_listings_active_featured` finds the few featured listings whatever else the filter asks.

### Text search

Work the search out first, forgiving typos and finding other forms of the words, along with the words it searched in place of misspelt ones:

```sql
SELECT query::text, corrections, kinds, kind_query::text FROM search_query(:words);
-- golff: 'golff' | 'golf', {golf}, {}, NULL
-- golf në shitje: 'golf', {}, {SELL}, 'shitje' | 'shitjes'...
```

Then pass the query in as a parameter, so the planner sees it, with the kinds the words named (a word that names one finds listings of that kind, or that say it):

```sql
SELECT l.id, l.title, l.sort_at
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.search_vector @@ :query::tsquery
  AND (l.listing_type = ANY(:kinds) OR l.search_vector @@ :kind_query::tsquery)   -- where kinds were named
ORDER BY l.sort_at DESC, l.id DESC
LIMIT 30;
```

For best-match ordering, use `ORDER BY ts_rank(l.search_vector, :query::tsquery) DESC`, as the best match first order does among the newest 240 matches, read off the newest first order with their own `LIMIT` so that only they are ranked (`push_ranked`). Searching the words exactly as typed is `websearch_to_tsquery('sq_unaccent', :words)`.

### Attribute filters

One EXISTS per filter, so filters combine with AND and a listing never appears twice:

```sql
SELECT l.id, l.title, l.price_amount, l.currency
FROM listings l
WHERE l.status = 'ACTIVE'
  AND l.category_id = ANY(:category_ids)
  AND l.price_normalized BETWEEN price_in_eur(:min, :currency) AND price_in_eur(:max, :currency)
  AND EXISTS (SELECT 1 FROM listing_attribute_values v      -- NUMBER: mileage <= 150000
              WHERE v.listing_id = l.id
                AND v.attribute_id = :mileage_attribute_id
                AND v.value_number <= 150000)
  AND EXISTS (SELECT 1 FROM listing_attribute_values v      -- SELECT: diesel or hybrid
              WHERE v.listing_id = l.id
                AND v.attribute_id = :fuel_attribute_id
                AND v.value_option_id = ANY(:fuel_option_ids))
  AND EXISTS (SELECT 1 FROM listing_attribute_options o     -- MULTISELECT: has navigation
              WHERE o.listing_id = l.id
                AND o.attribute_id = :features_attribute_id
                AND o.option_id = :navigation_option_id)
ORDER BY l.sort_at DESC, l.id DESC
LIMIT 30;
```

For "has all of these features", add one EXISTS per feature.

### Category subtree

```sql
WITH RECURSIVE subtree AS (
    SELECT id FROM categories WHERE slug = 'automjete'
    UNION ALL
    SELECT c.id FROM categories c JOIN subtree s ON c.parent_id = s.id
)
SELECT array_agg(id) FROM subtree;
```

The category tree is small and changes rarely, so the application can also keep it in memory.

### Listing form: attributes for a category, inherited from its ancestors

```sql
SELECT a.code, coalesce(a.name_i18n ->> :lang, a.name) AS label, a.data_type, a.unit, eca.required
FROM effective_category_attributes eca      -- own and inherited; the nearest category's settings win
JOIN attributes a ON a.id = eca.attribute_id
WHERE eca.category_id = :category_id
ORDER BY eca.sort_order;
```

### Start (or reopen) a conversation

```sql
INSERT INTO conversations (listing_id, buyer_user_id, seller_user_id, seller_business_id)
SELECT l.id, :buyer_id, l.seller_user_id, l.seller_business_id
FROM listings l
WHERE l.id = :listing_id
ON CONFLICT (listing_id, buyer_user_id) DO UPDATE SET updated_at = now()
RETURNING id;
```

A double click returns the same conversation instead of creating a second one.

### Inbox with unread counts

```sql
SELECT c.id, c.listing_id, c.last_message_at,
       (SELECT count(*) FROM messages m
        WHERE m.conversation_id = c.id
          -- the other side's: the buyer's for the seller's side, anyone else's for the buyer
          AND CASE WHEN c.buyer_user_id = :me THEN m.sender_user_id <> c.buyer_user_id
                   ELSE m.sender_user_id = c.buyer_user_id END
          AND m.created_at > coalesce(p.last_read_at, joined.at, '-infinity')
          AND m.deleted_at IS NULL) AS unread
FROM conversations c
LEFT JOIN conversation_participants p ON p.conversation_id = c.id AND p.user_id = :me
LEFT JOIN LATERAL (SELECT created_at AS at FROM business_members
                   WHERE business_id = c.seller_business_id AND user_id = :me) joined ON true
WHERE (c.buyer_user_id = :me OR c.seller_user_id = :me
       OR c.seller_business_id = ANY (ARRAY(SELECT business_id FROM business_members WHERE user_id = :me)))
  AND p.archived_at IS NULL
ORDER BY c.last_message_at DESC NULLS LAST
LIMIT 30;
```

A store's conversations are shared by its people (`db/messages.rs`): each takes part, a row in `conversation_participants` with their own read state, from their first message or read; until then, their count runs from when they joined the store.

Update `conversations.last_message_at` whenever a message is inserted.

INSERT INTO payment_webhook_events (provider, provider_event_id, event_type, payload)

ON CONFLICT DO NOTHING

- payment provider integration (until then, moderators give the promotions paid for by other means, `/promovo` saying to write in), and whether promotions are charged in lekë or euros (the seeded prices, and `HIGHLIGHT_7D`'s from migration 0040, are EUR placeholders)
- SMS/email provider integration
- image moderation/virus scanning
- rate limiting and anti-spam
- automated fraud scoring (duplicate photo hashes, new accounts posting high-value items)
- invoicing and tax: Albania requires fiscalised invoices (fiskalizimi) and VAT (TVSH) handling. Check with an accountant how this applies to online sales of promotions and subscriptions, and add what it needs (e.g. fiscal invoice codes) to the billing tables
- data retention for chat/audit logs
- backups, PITR, observability and disaster recovery
- partitioning or scheduled clean-up for the fast-growing tables: `messages`, `notifications`, `audit_log`, `listing_daily_stats`, `outbox_events`
- a sturdier source for the euro rate than the Bank of Albania's page the job reads (`rates.rs`): the bank sends its rates by e-mail on request, and a change to its page leaves the rate as it was until the parser follows it, with a warning in the log every six hours
- setting up the sign-in code channels (`src/sender.rs`, settings in `.env.example`), and turning test mode off (`SIGN_IN_CODES_ON_SCREEN=false`): e-mail by SMTP (Amazon SES, Postmark, Brevo...: SMTP_HOST, SMTP_USERNAME, SMTP_PASSWORD, EMAIL_FROM), and WhatsApp for phone numbers through Meta's WhatsApp Cloud API (a Meta business account, a WhatsApp Business phone number, an approved template of category Authentication with a "copy code" button, and a system user's permanent token: WHATSAPP_TOKEN, WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_TEMPLATE). A channel not set up writes its codes to the log. Phone numbers without WhatsApp need an SMS fallback, which needs WhatsApp's delivery webhooks to know when to use it. The notices of unread messages, the alerts of saved searches and the warnings of listings about to expire reach phone numbers only with a Utility template each (`WHATSAPP_NOTICE_TEMPLATE`, `WHATSAPP_SEARCH_TEMPLATE`, `WHATSAPP_EXPIRY_TEMPLATE`; their texts in the settings above, Meta's rules keeping a variable off a body's start and end), and their e-mails carry the one-click way to stop them that big mailboxes ask of bulk senders (`List-Unsubscribe` and `List-Unsubscribe-Post`, `web/unsubscribe.rs`), which counts only where the provider's DKIM signature covers those headers: check that with the provider
- naming the moderators (`MODERATORS` in `.env`): the review queue is built (`/moderim`: a new contact's first listing posted signed out and a listing with another seller's photos wait as `PENDING_REVIEW`, reported listings, suspended accounts, promotions), but without moderators nothing waits for review and the page answers no one
- a nightly clean-up of expired `sessions` and of `PENDING` accounts whose code never came back (sign-in codes over a day old already go, `db::forget_old_codes`, and listings posted signed out whose code nobody typed go after a day with their photos, `db::forget_drafts`)
- map tiles from a provider that allows production traffic (MapTiler, Stadia Maps, Thunderforest...) or from your own tile server, keeping the OpenStreetMap credit: OpenStreetMap's own tile server is for light use and may block a busy site. The tile URL is in `map_controller.js`
- PostGIS, if map search outgrows radius queries, e.g. to search inside an area drawn on the map
- a denormalised seller rating (count and sum) once review volume makes the per-seller aggregate noticeable
